# ADR-0011：热加必须主动告知在线客户端（informing layer）

- 状态：**Proposed**（实现与证据已就绪，待所有者确认后改 Accepted）
- 日期：2026-11-16
- 决策者：项目所有者（提出「做一个缓冲层，让玩家知情并做出正确决策」；实现与验证由 agent 完成）

## 背景

服务端热加一个**双端模组**时，已连接的客户端会陷入三种后果之一，严重程度不同，但都不轻：

1. **无感**（嫔/妃级、无注册表内容、不发包）：客户端什么都不知道，功能也拿不到。
2. **被踢**：客户端没有该 mod 的 payload channel，NeoForge 收到未知 channel 就断开
   （`multiplayer.disconnect.incompatible … (No Channel for …)`）。而我们为了让热加 mod 能发包，
   **已经修补了已建立连接的 `PayloadSetup`**——所以服务端会真的发出去，客户端才断；原本「服务端自己拒绝发送」的干净失败被换成了客户端掉线。
3. **被踢且进不来**（贵妃级注册表内容 + datapack）：实测（2026-11-16 11:48，专用服 + 未装该 jar 的客户端）：
   - 服务端 commit 注册表 → datapack 重载 → 客户端解码 `clientbound/minecraft:update_recipes` 失败
     （配方引用了它不认识的物品）→ 断开；
   - 之后重连时，登录同步的注册表快照含它不认识的条目 → NeoForge `server-with-unknown-keys` 再次断开。
   → **在装上同一个 jar 之前，这名玩家进不来**。这本来和「服务器启动时就装了该 mod」的语义一致，
     但热加把它变成了一次**在玩家在线时**发生的、不可撤销的降级。

客户端拿不到补救信息：mod 名、版本、jar 文件名、为什么被踢——全都没有，只有一条 Netty 解码栈。

## 决策

1. **无条件告知**：只要服务端热加成功，就向所有在线玩家发一条 `modreloader:server_mod_notice`
   （`ServerModNoticePayload`）：modId、显示名、版本、jar 文件名、jar 的 sha256 前 8 位、tier、是否注册表内容。
   **不分 tier、不论副作用大小**——「无感」的那一类同样需要知道（玩家才有机会自己去装）。
2. **发送时机在会伤害客户端的那几步之前**：notice 在 `FmlEvents.construct` 之后、`RegistryStage.commit` / datapack 重载之前发。
   实测过反例：放在管线末尾时，notice 到达的是一条已经被 `update_recipes` 弄死的连接，等于没发。
3. **客户端把事实变成可执行的句子**：聊天栏 + toast，两条文案——
   - 已有该 mod：「服务端新增了 X 版本；本客户端已有。」
   - 没有该 mod：「**服务端正在热加 X 版本**（jar、sha256…）。你没有：**你很快会被断开，并且在把同一个 jar 放进 mods/ 并重启之前无法重新进入**。在你自己的客户端热加它也可以。」
     最后一句是唯一真正有效的行动指引，必须写出来。
4. **客户端回报它有什么**：`modreloader:mod_notice_ack`（`ModNoticeAckPayload`）带 `knownModIds`；
   服务端记一行日志（`Dev has [] of the hot-added mod id(s)…`），管理员因此知道谁需要装。
   目前**只是告知**，不据此门禁任何行为（见「后果」）。
5. **服务端在不可逆提交前再吼一声**：有玩家在线 + 注册表内容时，引擎在 commit 前打一条 WARN：
   「N 个玩家在线；注册表内容不可撤销，未装该 mod 的客户端会被 datapack 同步踢掉且无法重连」。
6. **不做自动同步承诺**：jar（类）、资源（贴图/模型）、payload channel 都无法从服务端推过去；能同步的只有注册表 id 映射，
   而它要求客户端本地已经有这些条目。所以文案里不写「会自动装好」。

## 后果

- 玩家的知情问题解决：被踢之前会看到原因和下一步；管理员能看到谁缺什么。
- **不解除**「客户端没装 = 被踢 + 进不来」这个事实。它是 NeoForge 的正常语义（服务端有、客户端没有），
  我们的缓冲层让它**可解释、可提前准备**，不能让它不发生。
- 仍有竞态：notice 是 play payload，发出去到客户端处理有往返；如果 mod 在构造期就发包，仍可能先断。
  ADR 里明确这是 best effort。
- 未决（需要所有者拍板）：**是否默认拒绝**在有玩家在线时热加注册表内容（要求显式 `--force`），
  还是保持「警告 + 告知」。现在的实现是后者：不改变加载语义，只把信息给到位。
- 未决：`PayloadSetup` 修补对「没有该 channel 的客户端」是否应该跳过（那会让热加 mod 的发包在服务端就失败，
  比踢客户端干净，但需要客户端先回报，存在时序问题）。

## 备选（未采用）

- **只发一条通用「服务器内容已变化」**：玩家仍然不知道该装哪个 jar，等于没说。
- **等客户端确认后再提交注册表**：客户端只能回「我有没有这个 id」，在它没有这个 mod 的情况下永远无法「准备好」；
  而且会把服务端卡在一个待确认状态里（管理员没法继续）。
- **把通知做成聊天命令 `/modreloader why`**：需要玩家在断线之后才能查，且玩家根本没有这个 runtime 的上下文；
  被踢的瞬间能看到的只有聊天栏，所以推送式通知是唯一有效位置。
