# ADR-0015：玩家侧零手工——能力由运行时自动准备，不删能力

- 状态：**Accepted**（所有者 2026-11-18 修正：“能帮就帮，谁让你逃避了？”）
- 日期：2026-11-18
- 决策者：项目所有者

## 背景

热加的一部分能力依赖 JVM 级开关（JBR 的增强重定义、实验性 late AT）。
曾经把这些写进玩家路径（装 JBR 的步骤、手填 `-XX…` / `-D…`），玩家要下载、解压、
在启动器里改 Java、加参数，每一步都可能错。

最初的过度解读是“那就把 JBR 从玩家界面删掉、只留重启”——那是**逃避**：能力还在，
只是不帮玩家用。所有者明确否定了这个方向。

## 决策

1. **安装/解压是玩家动作的上限**：JBR 可以作为产品的一部分；玩家最多自己下载、安装、解压 JBR，
   之后由运行时找到它并接管（不改启动器 Java、不填 JVM 参数）。能自动下载/解压时，连这一步也不要求。
2. **统一能力模型**：JBR 重启一次性带上 `-XX:+AllowEnhancedClassRedefinition` 和
   `-Dmodreloader.lateAt=true`。玩家只感知一句话：**用 JBR 重启后，需要 JBR 的模组就能热加**。
   不按模组区分“只要 flag / 还要 lateAt”，玩家界面不出现这两个开关名。
3. **能力不删**：
   - JBR 已存在（实例目录、旁边、或已安装）→「用 JBR 重启」一键完成；
   - JBR 不存在 → 运行时**自动下载/安装** JBR 21（官方来源、校验、平台识别），或由整合包预置；
   - 离线/下载失败/启动器不支持自动重启 → 最后手段是「放 mods/ 后重启」；这是**产品失败信号**，要记录并修，不增加步骤，也不当成正常路径。
4. **重启 = 产品失败（切到 JBR 本身除外）**：一旦运行时已经是 JBR，任何模组仍然要求玩家重启才能加载，
   都是产品的缺口（bug/待修项），要记录并消除；**只有“把运行环境切到 JBR”这一次重启不算失败**。
   「放 mods/ 后重启」只能是最后手段与失败信号，不能当成正常产品路径。
5. **参数差异只存在于内部证据**：白名单的「额外参数」、`lateAt`、`-XX` 等只给包作者、管理员、开发者
   （[guides/jbr.md](../guides/jbr.md)）与我们的验收记录；不进玩家界面、不要求玩家理解。

## 后果

- 需要 JBR 的模组对玩家仍然可用，只是准备过程自动化；
- 玩家只做“安装/解压”这一种手工动作（且能自动时不必做），之后是“点一次重启”；
- 玩家可见文案不得出现 `lateAt`、`-XX`、`-D` 等开关名；per-mod 参数差异只留在内部证据；
- 做不到自动准备时，降级是“放 mods/ 重启”，但这是**产品失败**（要记录、要修），不是可接受路径；
- “切到 JBR”的一次重启不计入失败；除此之外的每模组重启都要进缺口清单；
- 运行时需要承担：平台/架构识别、下载与校验、解压、失败回滚、离线提示；
- 不引入“让玩家配置 JVM”的路径；文档中的手动步骤只作为开发者/包作者的兜底。

## 备选（未采用）

- **删掉玩家侧 JBR 能力、只留重启**：这是逃避，不是帮助（本次已回退）。
- 把 JBR 打进 mod jar：体积/许可/更新不合适（此前已否）。
- 让玩家在启动器里手填参数：产品失败（ADR 本条的主要动机）。
