# ADR-0002：采用 T0–T5 分层模型

- 状态：Accepted
- 日期：2026-11-14
- 决策者：项目所有者 + agent

## 背景

“这个模组能不能热重载”通常是二值问法，但实际代价差几个数量级：

- 改一张材质：按 `F3+T`；
- 改一个配方：`/reload`；
- 改一行代码：类重定义；
- 加一个方块：注册表 + 存档 + 网络协议，基本要重启。

如果只输出“能/不能”，用户无法理解原因，也无法做产品决策。

## 决策

采用 **T0–T5 + T?** 分级：

| Tier | 含义 |
|---|---|
| T0 | 只有资源 |
| T1 | 只有数据 |
| T2 | 代码，无 mixin、无注册表 |
| T3 | 代码 + Mixin，无注册表内容 |
| T4 | 注册表内容；需要世界/游戏层重启 |
| T5 | 不支持热换；完整重启 |
| T? | 分析失败 |

三条解释：

1. **Tier = 最低安全机制**，不是成功保证。
2. **T4 vs T5**：T4 是“当前做不到，但软重启有戏”；T5 是“连软重启也不建议”。
3. **Tier 必须带 confidence + reasons**；只给数字不算可解释。

## 后果

正面：

- 报告、UI、路线图、ADR 共用同一套语言。
- 能把“为什么必须重启”讲清楚。
- 为 T4 软重启划出明确的产品边界。

负面：

- 分级是启发式，可能误判（如 `mekanismgenerators` 通过 Mekanism API 注册，被标成 T2）。
- T5 可能过保守（AE2 因渲染 mixin 被判 T5）。
- 需要持续用真实切换做校准。

缓解：

- 所有预测都带 reasons 和 confidence。
- 后续接 dry-run / 运行时证据修正静态预测。
- 语料人工标注，算准确率/混淆矩阵。

## 备选（未采用）

- **二值“能/不能”**：信息量太低，无法解释。
- **只按加载器/模组类型分类**：与真实代价不相关。
- **直接叫 Level 0–5**：可以，但当前代码/文档已用 Tn，改名收益低（见术语表）。
